## 实现状态（2026-11-08）

第一版骨架已经落地：

- 插件：桥接、事件差分、跨会话 SQLite 记忆、知识库、Boss 1~3 条随机建议、面板、LLM 工具；
- 游戏侧：JS 只读状态 + UMG 字幕，UE4SS Lua 读 `reply.txt` 并驱动字幕（F10 开关）；
- TTS：插件只发 `respond`，宿主生成/播报，插件从 `ctx.bus.conversations` 取最终文本回写字幕；
- 独立 LLM：复用 `neko_arcade` 的客户端，负责会话记忆摘要与知识整理；最终台词仍归宿主；
- 独立性：LLM 客户端已 vendor 到本插件，运行时不 import 其他插件；游戏 Mod 不依赖
  `PBZQuestGuide` / `pbz-map-helper`，`Library/TsHelper` 仅可选并有原生回退；
- LLM 优先级：独立 LLM（已配置）→ 宿主主体 LLM（未配置时自动回退）→ 本地规则；
- 面板：按《影之刃零》重做为“影帐”战报台（战局/交锋/忆卷/百晓/灵犀/调息），不是照搬小游戏面板；
- 部署：`scripts/deploy.ps1` 已同步到两个活插件目录与游戏 Mod 目录。
- 持久化：配置拆为 `data/config/{general,llm,ui}.json`；记忆按存档分目录，
  Boss/会话/事实/偏好/约定分别落盘；旧 SQLite 自动迁移；知识种子复制到持久 data。
- 装备：按游戏实际分类拆成主/副武器、影之武装、饰品、药瓶/快捷道具多槽位；
  读取装备组件/角色属性，不回退背包；缺失时显示空槽。
- 知识库：拆为 Boss/小怪/铃铛、装备、机制、玩法库、区域与建议种子；首批 98 个实体、
  19 条已验证建议、9 条待实机核验；百晓按类型筛选并显示覆盖统计。
- 视觉：复用宿主视觉模型；F11 截取 PBZ 窗口，`pbz_look` 工具返回 image part；
  不持续录屏、不截桌面、不自建视觉模型。
- 界面：水墨卷轴/戏台花窗/江湖战报/青绿山水四套结构风格 × 四套辅助配色，
  舒适/紧凑密度、90%~115% 缩放、减少动效、
  任务/铃铛卡片、NEKO 羁绊、Boss 百晓情报、灵犀首页摘要与忆卷导出。
- 视觉：水墨山影/朱砂日轮/戏曲印章/竖排游戏名混合；独立“侦察”页提供大罗盘、
  Boss/小怪/铃铛详情与手动刷新；底部居中显示游戏名与 PBZ × N.E.K.O 联合标题。
- 跨风格常驻：侧栏 N.E.K.O 标识、战局侦察摘要条、四风格专属徽记（卷/戏/战/山）不会在切换风格后消失。

## 0. 一句话结论

能做，而且这个游戏比大多数单机游戏更适合做陪玩：

- 游戏里已经装了 **UE4SS（Lua + 原生 Bridge）** 和 **PuerTS JavaScript 运行时 + PBZModLoader**；
- 已有社区 Mod 证明可以读任务、背包、地图、铃铛、战斗状态，并往原生 HUD 上叠加 UMG 控件；
- 我们已有的 `neko_terraria` 插件已经跑通了「感知 → 场景判断 → 情绪 → 主动说话 → 宿主 LLM/人设 → 陪玩 UI」整条链路。

所以第一版不是"能不能做"，而是"哪些信息稳定可读、哪些必须靠画面识别、话术怎么不烦人"。

## 1. 目标与非目标

### 1.1 必须实现的目标

1. **懂游戏**
   - 认识 Boss、精英怪、小怪类型，知道大致的战斗思路（格挡/闪避/破韧/远程/群怪处理）。
   - 认识存档铃铛：知道它是检查点/复活点/补给点，会在合适的时候提醒先敲铃。
   - 知道当前区域、当前任务目标、前方大概有什么敌人。
2. **看得懂局面**
   - 玩家血量、受伤、连续受击、低血、死亡、复活、胜利。
   - 战斗开始/结束、Boss 出场、Boss 阶段变化、敌人数量与方向。
   - 任务推进、拾取关键物、靠近铃铛/商人/机关。
3. **像猫娘在陪玩**
   - 台词来自宿主当前猫娘人格，换角色/改人设后自动跟着变。
   - 战斗紧张时短、快、少；探索时能闲聊；死亡时安慰但不阴阳；胜利时真心夸。
   - 不抢话、不复读、不打断过场、不剧透没到的剧情。
4. **能问能答**
   - 玩家问"前面有什么怪""这个 Boss 怎么打""铃铛在哪""我该往哪走"时，能基于当前状态 + 知识库回答。
5. **画面识别兜底**
   - 结构化数据读不到（新怪、Boss 阶段、UI 状态）时，能截当前游戏画面给视觉模型判断，而不是瞎编。
6. **懂当前配装，但不翻背包**
   - 只读"身上穿着的东西"：当前主武器、影之武装、饰品等；**不读背包、仓库、材料数量**。
   - 知道武器/影之武装的铸魂形态与材料来源（知识层），但不知道玩家手里有几个材料，也不假装知道。
   - Boss 前可以结合"已装备的这套"和 Boss 知识给一条搭配建议；不自动换装，不评价没有的装备。
   - 没有数据就明说，不用背包数据补齐。

### 1.2 明确不做（第一版）

- **不自动代打**：不注入攻击/闪避/移动，不做自动战斗脚本。
- **不改存档、不改数值**：默认只读；写操作只限插件自己的桥接文件。
- **不读取背包/仓库/材料数量**：只读当前装备。涉及材料时只讲"需要什么、去哪拿"，不报"你有几个"。
- **不做全自动寻路/导航**：现有地图 Mod 已有寻路能力，陪玩第一版只做"观察 + 提醒"，避免两套导航打架。
- **不搬运第三方攻略库**：不整包复制 `PBZQuestGuide` 的攻略文本；知识库自建，运行时学习，尊重原作者与剧透边界。
- **不承诺游戏更新后永久可用**：非官方 Mod API，补丁可能改类名/签名，需要适配层和降级。

## 2. 已勘察到的事实（证据）

以下不是猜的，是直接读本机安装目录得到的。

### 2.1 游戏与运行时

| 项 | 结论 | 证据 |
|---|---|---|
| 游戏 | Phantom Blade Zero（影之刃零） | `platform\steam\PBZ.exe` 版本信息 |
| 引擎 | Unreal Engine 5 | `Engine\Config`、`Content\Paks\*.utoc/.ucas` |
| Steam AppID | 4115450 | `steamapps\appmanifest_4115450.acf` |
| 脚本 Mod | PuerTS（JS/TS）+ 自定义 `PBZModLoader` | `ProjectPBZ\Content\JavaScript\PBZModLoader` |
| 原生 Mod | UE4SS（Lua + C++ Bridge） | `platform\steam\ue4ss\UE4SS.dll`、`Mods\PBZQuestGuide\Native\Bridge.dll` |
| 热重载 | 支持，`mod.stop()` 后可重载 | `PBZModLoader\manager.js` |

### 2.2 现有 Mod 已经证明的能力

#### `PBZQuestGuide`（任务攻略 Mod）

- 读取任务：`PBZBlueprintFunctionLibrary.GetPBZNarrativeComp(context)` → `QuestList`
  - `quest.IsQuestComplete()`、`quest.QuestCompletion`（`EQuestCompletion`）
  - `quest.Branches`、`QuestTasks`（`CurrentProgress` / `RequiredQuantity` / `IsComplete`）
- 读取背包：`PBZBackPackSubsystem.Inventories.Get(itemId).CurrentAmount`（技术可行；本插件**设计上不读取**）
- 读取地图：`MapSubsystem.GetCurrentMapID()`、`GetLayerByLocation()`
- 读取标签：`EventPipelineManager.HasTagWithOutSource(tag)`、`CacheTags.Tags`
- 写文件：`UE.EasyCsv.SaveStringToFile(...)`（可写诊断/桥接 JSON）
- 叠加 HUD：`hud.WidgetTree.RootWidget` → 找 `CanvasPanel` / `Overlay` → `UE.NewObject(UE.Border/TextBlock)` → `AddChildToCanvas` → 设置锚点/位置/大小/ZOrder
- 热键：UE4SS Lua `RegisterKeyBind(Key.F8, ...)`、`LoopAsync(500, ...)`

#### `pbz-map-helper`（地图增强 Mod）

- 取玩家角色：`UE.PBZBlueprintFunctionLibrary.GetPBZLocalCharacter(context)`
- 取位置/朝向：`K2_GetActorLocation()`、`GetPlayerCameraManager(...).GetCameraRotation()`
- 取 GAS：`UE.AbilitySystemBlueprintLibrary.GetAbilitySystemComponent(character)`
- 读战斗状态标签：
  - `CharacterState.InCombat`
  - `CharacterState.Space.Air`
  - `CharacterState.StatusInfliction`
  - `CharacterState.Action`
  - `CharacterState.Crouching`
  - `CharacterState.ShipNavigation`
- 交互状态：`PBZInteractComponent.GetInteractComponent(pawn).GetInteractingActor()`
- 铃铛：`BellManager.ActivateBellIDs`、`DisableTeleportBellIDs`、`BellManager.GetBellData(id)`
- 存档系统：`PBZSaveLoadSubsystem`（GameInstanceSubsystem）
- 场景对象扫描：`GameplayStatics.GetAllActorsOfClass(context, Class.StaticClass(), out)`

> 这说明「玩家位置、战斗状态、铃铛、任务」都有稳定的结构化入口，不需要靠截图猜（背包同样可读，但本插件设计上排除）。

### 2.3 尚未确认、需要 P0 探针的字段

这些必须进游戏跑一次 API 探针才能定，现在不能写死：

1. 玩家生命值/最大生命值的 GAS AttributeSet 类名与属性名（如 `Health` / `Hp` / `CurrentHealth`）。
2. 敌人基类/精英/Boss 的类名，以及是否能直接读 `HP`、`MaxHP`、`Level`、`TeamID`。
3. 伤害事件来源：是否有可 Hook 的 `ReceiveDamage` / `PostGameplayEffectExecute`，还是只能靠血量差值推断。
4. Boss 阶段字段/UI 状态字段（是否可从 GAS Tag 或 Boss AI 组件读）。
5. 游戏内过场/菜单状态（用于闭嘴，避免过场时猫娘刷话）。

> 设计上会把「游戏 API 访问」全部收口到 `game_api.js` 一个适配层；上面任何一项变了，只改这一层。

## 3. 能力分级：哪些靠数据，哪些靠眼睛

| 级别 | 数据来源 | 能做什么 | 稳定性 |
|---|---|---|---|
| L1 结构化 | 游戏 UObject/GAS/子系统 | 位置、地图、任务、铃铛、战斗 Tag、交互状态（背包可读但设计排除） | 高 |
| L2 需探针 | 敌人 Actor/GAS 属性 | 血量、敌人数、Boss、伤害、阶段 | 中（需 P0 确认） |
| L3 视觉 | 窗口截图 + 视觉模型 | 新怪识别、招式前摇、Boss 阶段、场景氛围、UI 状态 | 中（受遮挡/分辨率影响） |
| L4 知识 | 自建知识库 + LLM 归纳 + 运行时学习 | 打法建议、机制解释、区域提示 | 取决于知识质量 |

**原则**：能用 L1/L2 就不截图；截图只在事件触发、未知敌人、Boss 阶段变化、用户主动问时抓，避免持续占用显卡与 API。

## 4. 总体架构

```text
┌──────────────────────────── 游戏进程（PBZ.exe） ────────────────────────────┐
│  pbz-neko-companion（PuerTS JS Mod）                                        │
│    ├─ game_api.js      读玩家/敌人/任务/铃铛（唯一适配层）                  │
│    ├─ state_sampler.js 4Hz 采样，差分出事件                                  │
│    ├─ bridge_writer.js 写 state.json / events.jsonl                         │
│    ├─ overlay.js       读 reply.json，UMG 字幕气泡                          │
│    └─ main.js          生命周期 + stop() 热重载                             │
└───────────────────────────────────┬─────────────────────────────────────────┘
                                    │ 命名管道（首选）/ JSON 文件（兜底）
┌───────────────────────────────────▼─────────────────────────────────────────┐
│  N.E.K.O 插件 neko_pbz（Python）                                            │
│    ├─ bridge/        读状态、事件去重、心跳检测                              │
│    ├─ perception/    场景分类、前方敌人扫描、截图 + 视觉                      │
│    ├─ knowledge/     Boss/小怪/铃铛/区域知识库与检索                          │
│    ├─ companion/     情绪弧线、说话冲动、冷却、防复读                         │
│    ├─ llm/           宿主 __call_llm / call_vision + 工具                    │
│    └─ entries/       @lifecycle、@plugin_entry、@llm_tool、@ui.context       │
└───────────────────────────────────┬─────────────────────────────────────────┘
                                    │ 宿主能力
                          ┌─────────▼──────────┐
                          │ 猫娘人设 / LLM / TTS │
                          │ 聊天窗 / 面板 / 记忆  │
                          └────────────────────┘
```

### 4.1 为什么用「游戏内 Mod + Python 宿主插件」

- PuerTS 在游戏里能读 UObject、画 UMG，但没有 Node 的 `fs`/`net`；不适合直接调 LLM。
- Python 侧有宿主 LLM、人格、TTS、记忆、聊天窗，适合做"大脑"。
- 两边用文件/管道解耦：游戏崩溃不会拖死插件，插件重启不需要重开游戏。

### 4.2 通信选型

| 方案 | 延迟 | 稳定性 | 结论 |
|---|---|---|---|
| 命名管道 | 1–10ms | 好，但 JS 侧需要原生能力 | **首选**，P0 验证 PuerTS 是否能调用 |
| JSON 文件轮询 | 50–250ms | 很好，`EasyCsv.SaveStringToFile` 已证明可写 | **保底方案**，第一版可直接用 |
| WebSocket | 10–50ms | JS 侧无 Node net；需额外 C++ | 暂不选 |
| HTTP | 10–50ms | 同上 | 暂不选 |

第一版建议：**文件桥接先跑通，接口按管道协议设计**，后续换管道不改业务层。

### 4.3 目录约定

```text
%LOCALAPPDATA%\N.E.K.O\pbz_bridge\
  ├─ state.json          游戏 → 插件（4Hz 覆盖）
  ├─ events.jsonl        游戏 → 插件（追加事件）
  ├─ reply.json          插件 → 游戏（最新一条台词）
  ├─ heartbeat.json      双向心跳
  └─ screenshot.jpg      插件临时截图（不长期保存）
```

所有文件带 `version` / `seq` / `ts`，插件检测到超过 2 秒未更新就显示"感知断开"，不继续用旧血量瞎说。

## 5. 游戏知识系统（本方案的核心）

「猫娘不懂游戏」不是靠一句系统提示词解决的，必须有可检索、可更新、能区分事实与猜测的知识层。

### 5.1 三层知识

```text
① 通用战斗知识（稳定）
   近战怪 / 远程怪 / 盾怪 / 精英 / 群怪 / Boss 的通用处理原则

② 具体条目知识（按游戏版本维护）
   Boss 名称、区域、阶段、弱点、推荐应对、掉落、是否可跳过
   小怪名称、攻击类型、危险动作、优先击杀顺序
   铃铛名称、区域、作用、附近商人/机关/分支

③ 运行时事实（每局实时）
   当前有多少怪、什么方向、谁在仇恨、Boss 血量、玩家血量
```

回答时必须先引用 ③，再引用 ②，最后才是 ① 的通用建议。不能拿知识库里的"某地有 Boss"当成"你眼前就是它"。

### 5.2 知识条目结构

```json
{
  "id": "boss.ah_hua",
  "type": "boss",
  "names": ["新娘阿花"],
  "aliases": ["阿花"],
  "region": "悲泣溪谷",
  "source": "runtime|vision|curated",
  "confidence": 0.95,
  "spoiler_level": 1,
  "phases": 2,
  "danger_moves": ["红绸突进", "召唤傀儡"],
  "recommended": ["保持中距离", "突进后摇再反击", "优先清理召唤物"],
  "punish_window": "突进落空后的短暂硬直",
  "notes": "具体招式名以实机识别为准，未确认时不编造"
}
```

小怪条目同理，但字段是：`archetype`（近战/远程/盾/自爆/群）、`threat`（低/中/高）、`priority`、`tip`。

### 5.3 知识从哪来

| 来源 | 用途 | 可信度 |
|---|---|---|
| 游戏内类名/数据表/UI 文本 | 名称、ID、区域、是否 Boss | 最高 |
| 运行时观察（实际遇到） | 数量、招式、阶段、死亡次数 | 高 |
| 视觉模型识别 | 新怪外观、动作前摇、场景 | 中，需置信度 |
| 人工整理 | 打法建议、机制解释 | 高（需标注版本） |
| 玩家纠正 | "这不是 X，是 Y" | 高，写入记忆 |

**不整包复制第三方攻略 Mod 的文本**。可以借鉴其"哪些字段可读"的技术结论，但知识内容自建，避免版权与剧透争议。

### 5.4 "前面有什么怪"怎么实现

1. 取玩家位置与镜头朝向。
2. 以玩家为原点，做 **前向 120° 锥形、25~40 米** 的敌人筛选（优先用引擎的 `GetAllActorsOfClass` 或 AI 子系统，避免全场景遍历）。
3. 对每个敌人算：距离、方位（左前/正前/右前）、是否隔墙（LineTrace）、是否仇恨玩家。
4. 按原型聚合：`右前方 3 只：2 近战 + 1 远程，约 18 米，尚未发现你`。
5. 若结构化敌人列表不可用 → 触发一次视觉识别，输出同样的结构。
6. **不轻易说"安全"**：只描述"扫描范围内未发现敌人"，不说"前面没危险"。

### 5.5 存档铃铛怎么讲

铃铛在本作中是检查点/复活点体系（现有 Mod 通过 `BellManager.ActivateBellIDs` 读取已激活列表）。陪玩要做的不是背坐标，而是：

- 靠近未激活铃铛（例如 8 米内）→ 提醒"先把铃敲了"；
- 敲铃后（激活列表新增）→ 确认存档/复活点已更新；
- 进入明显 Boss 区域前、且附近有未激活铃铛 → 强提醒一次；
- 玩家死亡后 → 告知会回到哪个铃铛，而不是泛泛安慰；
- 发现新铃铛 → 记录到长期记忆，后续可以回答"这附近哪个铃最顺路"。

> 铃铛名称从 `BellManager.GetBellData(id)` + 地图数据取；取不到时只报"检查点已激活"，不编名字。

### 5.6 知识缺口怎么处理

- 未知敌人：标记 `unknown`，用视觉 + UI 名称补全；仍不确定就诚实说"这只喵还没认出来，先别硬吃招式"。
- 版本更新：知识条目带 `game_version`，版本不匹配时降级为通用建议。
- 冲突：运行时事实优先于知识库；玩家纠正优先于两者。

### 5.7 知识域全景（装备 / 武器 / 影之武装 / 铸魂）

游戏里的知识量远不止 Boss。知识库必须按"实体 + 关系"建，否则无法回答"这把武器怎么升""这个材料在哪""我该带什么影之武装"。

| 领域 | 典型条目 | 关键字段 | 陪玩用途 |
|---|---|---|---|
| 主武器 | 黑伤、双刃、长形黑伤、各类刀剑 | 类型、招式、强化等级、升级材料、获取方式、适用场景 | 换武器时解释、升级提醒、Boss 前建议 |
| 影之武装 | 巨凶斧、羽弓、追命锁镰、虎炮等 | 类型（破障/远程/位移/控制）、充能、冷却、适用地形/敌人 | 提示"这里需要什么武装"、战斗中提醒可用 |
| 饰品 | 生命、杀气、格挡、闪避、掉落类 | 效果、叠加规则、获取来源 | 配装建议、缺什么饰品 |
| 消耗品 | 药葫芦、各类药剂 | 回复量、持续时间、冷却、来源（知识） | 低血时只建议类型，不报玩家持有数量 |
| 升级/铸魂材料 | `Item_Weapon_TierUp_*` 系列 | 对应武器、需求量、掉落/商店来源 | 讲需求和来源，**不读持有量** |
| 铸魂系统 | 武器/影之武装的铸魂形态（如催心琵琶→幻术琵琶） | 当前形态、下一形态、铸魂材料、前置条件、新能力 | 形态链、材料需求与来源、铸魂后能力解释 |
| Boss | 名称、区域、阶段、危险招式 | 弱点、应对、掉落、是否可跳过 | 战前提示、阶段反应、死亡复盘 |
| 小怪 | 近战/远程/盾/自爆/群怪 | 威胁、优先击杀、危险动作 | "前面有什么怪"、战斗建议 |
| 铃铛/区域 | 检查点、地图层、商人、机关 | 激活状态、邻近内容 | 导航、存档提醒 |
| 任务 | 主线/支线/收集 | 目标、进度、前置、奖励 | 追踪、提醒、防漏 |
| 机制 | 杀气、格挡、闪避、处决、状态异常 | 触发条件、收益、代价 | 战斗中解释"为什么打不动/为什么没杀气" |

> **设计约束**：本插件不读背包。因此知识库中的"需求/来源"是确定的，"玩家是否拥有"是未知的。所有播报必须用条件句或提问，例如"这把铸魂需要 X，你先看看身上有没有"，不能说"你还差 2 个"。
>
> 如果玩家主动打开铸魂/升级面板并询问，可在**玩家同意**的前提下用画面识别读当前可见的缺口；不在后台读背包。

**统一知识条目结构**：

```json
{
  "id": "phantom_edge.brutal_axe",
  "type": "phantom_edge",
  "names": ["巨凶斧"],
  "aliases": ["斧子"],
  "game_version": "CL-302256",
  "source": "runtime|datatable|vision|curated|player",
  "confidence": 0.95,
  "spoiler_level": 1,
  "facts": {
    "category": "影之武装",
    "use": "破障/破墙",
    "charge": 1,
    "cooldown": 0
  },
  "relations": [
    {"type": "required_in", "target": "area.weeping_valley.dragon_pillar"},
    {"type": "dropped_by", "target": "boss.peng_meng"}
  ],
  "tips": ["看到可破坏墙体时先确认是否带了它"],
  "updated_at": "2026-11-07"
}
```

关系类型至少包括：`upgrades_to`、`requires_material`、`dropped_by`、`sold_by`、`located_in`、`counters`、`synergy_with`、`unlocked_by`。

**知识来源与可信度**：

| 来源 | 适合 | 可信度 | 处理 |
|---|---|---|---|
| 游戏 DataTable / 物品配置 | 名称、分类、升级链、数值 | 最高 | 运行时读表，版本号标记 |
| 装备子系统 | 当前穿戴的武器/影之武装/饰品 | 最高 | 实时快照（只读装备槽） |
| 背包/仓库 | 不读取 | — | 设计排除：不碰物品数量 |
| UI 文本 | 铸魂面板、材料说明、形态描述 | 高 | 视觉/文本读取 |
| 实战观察 | 招式、阶段、死亡原因 | 高 | 自动记录，需多次确认 |
| 人工整理 | 打法、路线、配装思路 | 高 | 带版本与剧透等级 |
| 玩家纠正 | "这不是 X" | 高 | 写入长期记忆并覆盖 |
| 第三方攻略 | 补充线索 | 中 | 不整包复制，只做交叉验证 |

**回答优先级**：当前装备/数值 → 当前敌人/区域 → 知识库条目 → 通用战斗原则。任何一层缺失都要明说，不能把"攻略里有"说成"你现在就是"。

### 5.8 知识库落地：存储、检索、更新

#### 存储

第一版用 SQLite，不用纯 JSON 硬扛：

```text
data/knowledge/pbz_knowledge.db
  entities(id, type, name, aliases, game_version, source, confidence,
           spoiler_level, facts_json, updated_at)
  relations(src_id, rel, dst_id, meta_json)
  observations(id, entity_id, field, value, evidence, confidence, ts)
  corrections(id, entity_id, field, old_value, new_value, player_id, ts)
  FTS5: entity_names(name, aliases)
```

- 种子数据放 `data/knowledge/seed/*.json`，首次启动导入；
- 中文名/别名走 FTS5；后续可选加向量检索，解决"那个能破墙的斧子"这种口语查询；
- 所有条目必须带 `game_version` 与 `spoiler_level`，否则不允许入库。

#### 检索能力

| 查询 | 返回 |
|---|---|
| `item_info("巨凶斧")` | 类型、用途、获取、升级、适用场景 |
| `upgrade_path("黑伤")` | 当前形态/下一形态、所需材料、来源（不含玩家持有量） |
| `boss_info(当前 Boss)` | 阶段、危险招式、应对、掉落、剧透过滤 |
| `bell_info(区域)` | 最近铃铛、是否激活、附近商人/机关 |
| `quest_status()` | 当前任务、目标、进度、相关地点 |
| `player_state()` | 血量、杀气、已装备武器/影之武装/饰品（不含背包） |
| `kb_search("破墙")` | 按用途反查影之武装/道具 |

这些同时暴露为 `@llm_tool`，让宿主猫娘在聊天中自然调用，而不是把整库塞进提示词。

#### 更新闭环

```text
游戏 DataTable / UI 文本
        ↓ 启动时读取
实体抽取 → 去重合并 → 版本标记 → 人工/规则校验 → 入库
        ↑
运行时观察（遇到怪、掉落、升级）→ observations
        ↑
玩家纠正（"这不是 X"）→ corrections（最高优先级）
```

- 游戏补丁：保留旧版本条目，标记 `stale`，不直接删除；
- 未知实体：进入 `unknown_queue`，面板可见，玩家可补名称；
- 冲突：玩家纠正 > 运行时观察 > 数据表 > 人工整理 > 第三方；
- 数值类结论必须附证据来源，没有证据就不说具体数字。

#### 质量红线

1. 不知道就说不知道，不编 Boss 名、招式名、材料名。
2. 不把"数据表存在"说成"你已拥有"。
3. 不把"攻略推荐"说成"唯一解"。
4. 剧透等级不够的条目，只给模糊提示或不提。
5. 版本不匹配的条目只作参考，并明确提示可能过期。

### 5.9 铸魂系统（Weapon Soul Casting）

铸魂不是普通的“等级 +1”，而是武器/影之武装的进阶与形态变化：消耗特定铸魂材料，解锁新能力、改变招式，甚至变成另一把武器。

**已确认的证据**：

- “铸魂”在现有游戏数据中出现 184 次，“铸魂材料”是独立物品用途；
- 例：催心琵琶铸魂后变为幻术琵琶，可破除幻术迷雾、可操控小怪；
- 例：长形黑伤铸魂可追加寒冰阶段，并产出黑伤双刀铸魂材料；
- 内部数据出现 `DT_WeaponSnapSoulText`、`ShaChiWeaponSnapSoulData`、`Item_Weapon_TierUp_*` 等表/资源。

**知识条目示例**：

```json
{
  "id": "weapon.cuixin_pipa",
  "type": "weapon",
  "names": ["催心琵琶"],
  "soulcasting": {
    "current_form": "催心琵琶",
    "next_form": "幻术琵琶",
    "materials": [
      {"id": "", "name": "弦者的琵琶部件", "qty": 0, "source": "任务/探索"}
    ],
    "prerequisite": "",
    "new_abilities": ["破除幻术迷雾", "操控小怪"],
    "changes_moveset": true
  },
  "source": "datatable+player",
  "confidence": 0.9,
  "spoiler_level": 2
}
```

**陪玩行为**：

| 时机 | 行为 |
|---|---|
| 玩家提到材料 / 主动询问 | 只讲“这把武器需要什么、去哪拿”，不判断玩家有没有 |
| 玩家说材料齐了 / 铸魂面板可见 | 提醒去找对应 NPC/地点（如幻鬼），不自动传送、不代铸 |
| 铸魂完成 | 解释新形态、新能力、适用地形/敌人，不只说“变强了” |
| 玩家问“值得铸魂吗” | 讲形态变化与场景价值；没有数值依据就不排名 |
| 铸魂影响后期内容 | 按剧透等级过滤，默认只提示“会解锁新能力” |

**边界**：只读，不消耗材料、不自动铸魂、**不读取背包/材料数量**；材料名与需求以数据表/知识库为准，玩家是否持有以玩家自述或可见面板为准；铸魂后的能力必须来自数据或实机确认，不能按名字猜。

### 5.10 内容研究计划（Boss / 小怪 / 玩法）

知识库不是一次性抄一份攻略，而是持续研究 + 实机核验。

**首批核验对象**（名字已在现有数据中出现，仍需实机确认招式与阶段）：

- Boss/精英：新娘阿花、痴狂暴徒：残钢、沐小葵、玉琮、追命、彭猛、雷当、玉瓒等。
- 小怪原型：近战刀兵、远程弓手、盾兵、重甲、自爆/机关、召唤物、群怪。
- 场景机制：铃铛、可破坏墙体、攀爬/钩锁点、机关、陷阱、地形杀。

**每个 Boss 条目至少记录**：

| 字段 | 说明 |
|---|---|
| `id` / `names` / `aliases` | 内部 ID、中文名、玩家常用叫法 |
| `region` / `arena` | 区域、战斗场地特征（狭窄/高低差/水域） |
| `phases` | 阶段数与阶段切换信号 |
| `attack_tags` | 突进/远程/范围/抓取/毒/召唤等 |
| `telegraphs` | 可观察的前摇动作 |
| `punish_windows` | 确认的惩罚窗口；不确定就留空 |
| `recommended_defense` | 格挡/闪避/拉开/绕后/破韧 |
| `adds` | 召唤物/小怪及优先击杀顺序 |
| `hazards` | 场地机关与环境危险 |
| `drops` | 关键掉落（按剧透等级显示） |
| `common_deaths` | 实机统计的常见死因 |
| `lore` | 背景故事，spoiler_level 控制 |

**每个小怪条目**至少记录：`archetype`、`threat`、`attack_tags`、`priority`、`tip`、`observed_count`。

**核验规则**：

1. 数据表/UI + 实机观察，至少两个独立来源；
2. 只有一次观察的招式标 `confidence: 0.5`，不写进确定建议；
3. 版本更新后重新跑探针，旧条目标 `stale`；
4. 玩家纠正优先；
5. 攻略级信息必须带 `spoiler_level`。

## 6. 感知与事件模型

### 6.0 玩家状态模型（重点）

玩家状态不是只有一个血量。第一版至少要分五组，按可读性逐级接入：

#### A. 生存（P0，必须）

| 字段 | 说明 | 来源 |
|---|---|---|
| `hp` / `max_hp` / `hp_percent` | 当前/最大生命 | GAS Attribute（名称待探针） |
| `dead` | 是否死亡 | 血量 + 死亡 Tag/UI |
| `damage_events` | 单次/短时间掉血 | 血量差分或伤害 Hook |
| `status_effects` | 中毒/流血/燃烧/冻结等 | GAS Tag / UI |
| `respawn_point` | 最近铃铛 | `BellManager` + 存档系统 |

#### B. 战斗资源（P1）

| 字段 | 说明 | 备注 |
|---|---|---|
| `shachi.current/max/percent` | 杀气 | 数据里大量使用，具体 Attribute 名待探针 |
| `stamina` / `posture` | 体力/架势（若存在） | 需 P0 确认 |
| `ultimate_charge` | 大招/绝技充能 | 若可读 |
| `combo` / `rank` | 连击/评价 | UI 或 GAS |
| `in_combat` | 战斗状态 | `CharacterState.InCombat` 已验证 |
| `action_state` | 攻击/受击/翻滚/处决 | `CharacterState.*` Tag |

#### C. 装备与配装（P1，用户明确要求）

| 字段 | 说明 |
|---|---|
| `main_weapon` | 当前主武器：id、名称、类型、强化等级、当前铸魂形态（可读时） |
| `secondary_weapon` | 副武器/备用武器（若有） |
| `phantom_edges[]` | 已装备影之武装：id、名称、充能、冷却、是否可用 |
| `accessories[]` | 饰品及效果 |
| `equipment_changed_at` | 最近换装时间（用于触发点评） |

> **不读背包**：不列出玩家拥有的其他武器、饰品、药品、材料；不统计数量。读不到就返回 `null`，不猜。

读取入口（已见或待探针）：

- 武器数据：`config_WeaponItemDatas_*`、`config_ShaChiWeaponItemDatas_*`（现有 Mod 里出现）
- **禁止**调用 `PBZBackPackSubsystem.Inventories` 做玩家持有量扫描（设计排除）
- 影之武装：`PhantomEdges_*` 数据与 `ShaChiWeapon` 相关接口
- 装备槽/当前武器：需 P0 找 `PBZEquipment*` / `PBZPlayer*` 子系统；找不到就用 UI 画面兜底，**不回退到背包**

#### D. 铸魂与成长（P2，用户明确要求）

| 字段 | 说明 |
|---|---|
| `equipped_soulcasting` | 当前装备武器的铸魂形态、下一形态（仅当前装备，可读时） |
| `soulcasting_catalog` | 知识库中的形态链、材料需求与来源（不是玩家持有量） |
| `level` / `exp` | 角色等级/经验（若游戏有） |
| `unspent_points` | 可分配点数（若有） |
| `unlocked_skills[]` | 已解锁招式/能力 |

#### E. 世界与目标（P1）

- 地图 ID、区域名、层数
- 当前任务与目标进度
- 铃铛（最近/已激活/未激活）
- 前方敌人组合
- 附近商人/机关/可拾取关键物

> 状态模型的原则：**先保证 P0 可读且稳定，再逐项加 P1/P2**。任何字段读不到就返回 `null`，不阻塞其他字段，也不要用旧值冒充新值。

#### 状态变化如何变成"陪玩"

| 变化 | 事件 | 猫娘该做什么 |
|---|---|---|
| 生命跌破 35% | `low_hp` | 短句提醒，优先报"还有没有药/能不能拉开" |
| 杀气见底 | `shachi_low` | 提醒不要硬拼，先拉扯/普攻回资源 |
| 换上新高强化武器 | `weapon_changed` | 认出新武器，说明变化，不空夸 |
| 影之武装就绪 | `edge_ready` | 遇到对应场景（破墙/远程/位移）才提醒 |
| 玩家说材料齐了 | `upgrade_claimed` | 提醒去对应 NPC；**不后台核对背包** |
| 进入 Boss 区且铃未激活 | `boss_gate` | 先提醒敲铃，再报 Boss 信息 |
| 死亡 | `death` | 先接情绪，再给一条可执行建议 |
| 胜利 | `victory` | 夸具体操作（弹反/闪避/处决），可提上次失败 |

### 6.1 状态采样

- 游戏内 4Hz（250ms）采样基础状态；战斗事件即时追加。
- 只读不写；所有字段读取都单独 `try/catch`，单个字段失败不影响整包。
- 采样在游戏线程的空闲回调里做，避免每帧扫描 UObject。

### 6.2 事件类型

| 事件 | 触发条件 | 优先级 |
|---|---|---|
| `session_start` | 进入世界/读档完成 | P2 |
| `zone_change` | `MapSubsystem` 地图 ID 变化 | P1 |
| `combat_start` | `CharacterState.InCombat` 或 20m 内敌人进入仇恨 | P1 |
| `combat_end` | 脱战 Tag 消失且 5s 内无近敌 | P2 |
| `enemy_spotted` | 前方锥形扫描首次发现敌人组合 | P1 |
| `elite_spotted` / `boss_spawn` | 精英/Boss 类或 UI 名称命中 | P0/P1 |
| `boss_phase` | Boss 血量跨阶段阈值 / 阶段 Tag 变化 | P0 |
| `player_damaged` | 血量下降超过阈值（如 8%） | P1 |
| `low_hp` | ≤35%（恢复到 45% 才解除） | P0 |
| `critical_hp` | ≤18% | P0 |
| `death` | 血量 ≤0 或死亡 Tag | P0 |
| `respawn` | 死亡后血量恢复且位置回到铃铛附近 | P0 |
| `victory` | Boss 死亡 / 战斗结算 | P0 |
| `bell_near` | 距未激活铃铛 <8m | P1 |
| `bell_activated` | `ActivateBellIDs` 新增 | P1 |
| `quest_progress` | 任务目标数值/分支状态变化 | P2 |
| `item_key` | 关键物/记忆之花/钥匙入包 | P2 |
| `stuck` | 位置 90s 内变化 <3m 且非菜单 | P2 |
| `cutscene` | 过场/菜单状态 | 静默 |

### 6.3 迟滞与去抖

- 低血：35% 进入、45% 退出，避免在阈值附近反复惊呼。
- 战斗结束：脱战后再等 5s，避免"假结束"。
- 敌人组合：同一组合 30s 内只播一次；数量变化 >50% 才重新播。
- 死亡/胜利：一局只播一次，除非玩家主动问。

## 7. 陪玩话术引擎

### 7.0 情感内核：她是陪玩的人，不是攻略机

**优先级：陪伴 > 情绪回应 > 游戏信息。**

- 先回应人，再回应局：玩家说"好难"，先接住情绪，别第一句就报按键。
- 信息只在有用时出现；普通探索不需要每 30 秒讲一条知识。
- 有记忆：上次卡在哪、喜欢哪把武器、怕什么怪、说过什么、约好下次再来。
- 有自己的情绪：会担心、会得意、会小吃醋式吐槽，但不操纵、不用内疚感留人。
- Boss 前最多给 1~3 条具体建议（随机、已验证），其余是陪伴；不要把聊天变成连续教程。
- 不知道就承认；不编"你刚才差点就赢了"这类没发生的事。
- 长局关心：连续玩很久或多次死亡时，提醒休息，不催着继续。
- 不贬低玩家、不嘲讽操作、不拿"别人都过了"施压。
- 玩家想安静时能安静；玩家想聊时能接住话题。

**闲聊必须贴地**（grounding）：

- 只引用 `state.json`、知识库、视觉结果、玩家原话里的事实。
- 没读背包 → 永远不说"你有/你没有某个物品"。
- 不确定敌人名 → 说"那只拿弓的"，不编专有名词。
- 不确定是否击杀 → 说"好像倒了"，等确认后再庆祝。
- 玩家纠正优先于知识库和视觉。

**情感节拍**：

| 场景 | 情感动作 |
|---|---|
| 第一次死亡 | 接情绪 + 一句安抚，不急着复盘 |
| 连续死亡 | 不嘲讽；问要不要换思路/休息；只给一条可执行建议 |
| 首次击败某 Boss | 记住这个时刻，之后再提 |
| 复仇成功 | 呼应上次失败："这次没让它碰到你。" |
| 长时间探索 | 聊风景/角色/玩家感受，不强塞攻略 |
| 玩家沉默 | 不刷屏；最多轻轻问一句 |
| 玩家烦躁 | 降频、短句、先顺从再建议 |
| 玩家分享 | 追问细节，让玩家感到被听见 |

### 7.1 三层生成

```text
第 1 层：事实短句（<300ms，保证及时）
  「右前方三只，有个拿弓的。」

第 2 层：人设台词（0.8~2s，LLM 生成）
  根据宿主猫娘人格 + 当前情绪 + 事实，生成 1~2 句。

第 3 层：深度点评（按需，视觉/知识）
  Boss 阶段变化、玩家问"怎么打"时，给具体机制与建议。
```

第 1 层永远可用；第 2 层失败就退回第 1 层；第 3 层失败就退回知识库条目摘要。

### 7.2 说话预算

| 优先级 | 场景 | 长度 | 冷却 |
|---|---|---|---|
| P0 | 死亡、残血、Boss 出场、阶段切换 | ≤16 字 | 20s |
| P1 | 战斗开始、发现精英、铃铛、前方怪群 | ≤24 字 | 45s |
| P2 | 区域变化、任务、拾取、闲聊 | ≤40 字 | 120s |
| P3 | 玩家主动提问 | 不限（≤120 字） | 即时 |

- 战斗中默认只播 P0/P1；P2 排队到脱战后。
- 过场/菜单/对话选项期间全部静默（P0 的死亡提示除外）。
- 同一 `事件+敌人+区域` 60s 去重；语义重复（LLM 判断或文本相似度）10 分钟去重。
- 连续两次没被玩家回应 → 主动降频，不刷存在感。

### 7.3 情绪弧线

| 情绪 | 触发 | 表现 |
|---|---|---|
| 紧张 | 战斗开始、Boss、低血 | 句子短、少语气词、聚焦当下 |
| 担心 | 连续受击、残血 | 提醒吃药/拉开距离，不责备 |
| 兴奋 | 完美格挡、处决、胜利 | 夸具体操作，不空喊"好厉害" |
| 骄傲 | 玩家多次击败同一 Boss | 提上次失败/这次进步 |
| 心疼 | 死亡、反复卡关 | 先接情绪，再给一条可执行建议 |
| 放松 | 探索、铃铛、安全区 | 可以闲聊、吐槽、讲知识 |

### 7.4 几条硬规则

1. 不预测未确认的机制；不知道就说不知道。
2. 不把"知识库里有"说成"你眼前有"。
3. 死亡时不说"你怎么又死了""这都不会"。
4. 胜利时夸具体点（"最后那下闪避接反击"），夸不出来就短夸。
5. 玩家明确说"别说话/安静"→ 进入静默模式，直到解除。
6. 剧透等级：0=只报眼前，1=区域/机制提示（默认），2=攻略级（需手动开启）。

### 7.5 配装 / 铸魂陪玩场景

| 场景 | 触发 | 陪玩内容 |
|---|---|---|
| 换武器 | `weapon_changed` | 认出武器类型、强化等级与铸魂形态；说清"这把适合什么"，不评价数值强弱除非有依据 |
| 玩家问升级/铸魂 | 玩家原话 | 讲需要什么材料、去哪拿、找哪个 NPC；**不报持有量** |
| 铸魂完成 | `soulcast_done` / 当前形态变化 | 解释新形态与新能力，不只说"变强了" |
| 杀气不足 | `shachi_low` | 提醒拉开、别硬吃大招；不机械喊"吃药" |
| 影之武装可用 | `edge_ready` | 结合场景：破墙、射落、位移、控制；没场景就不提 |
| 换饰品/装备 | `equipment_changed` | 说明当前效果与变化，问一句要不要换回来（不自动换） |
| Boss 前 | `boss_gate` | 结合已装备给一条搭配建议（见 7.7） |
| 死亡复盘 | `death` + 最近事件 | 说清"是杀气空了 / 没拉开 / 吃了远程 / 地形"等可验证原因 |
| 主动提问 | "这把武器怎么样""怎么升级" | 结合已装备与知识库回答；材料只讲需求/来源 |

**配装建议的边界**：

- 不凭稀有度断言强弱；优先讲机制与场景适配。
- 不自动更换装备、不自动使用材料。
- 数值比较只在能读到真实数值时做；读不到就说"喵看不到具体数值"。
- 不读背包，不报"你有几个材料"；所有持有量相关问题交给玩家自述或可见面板。
- 玩家有自己的玩法时，建议只做参考，不反复纠正。

### 7.6 任务追踪 / 铃铛导航 / 战斗闲聊

#### 任务追踪

| 时机 | 行为 |
|---|---|
| 接取/推进任务 | 记下任务名、当前目标、数值进度，不急着播 |
| 目标变化 | 一句话报"下一步做什么"，不念整段任务文本 |
| 玩家离开相关区域 | 提醒一次"这个任务目标在刚才那片区域" |
| 玩家长时间无进展 | 只给一条可执行线索，不连续催 |
| 任务完成 | 确认完成 + 奖励要点 + 下一步可选方向 |
| 隐藏/剧透任务 | 默认不主动提，玩家问才按 spoiler 等级回答 |

实现上读 `PBZNarrativeComponent.QuestList` 与 `QuestTasks.CurrentProgress/RequiredQuantity`，不改任务状态。

#### 铃铛导航

| 时机 | 行为 |
|---|---|
| 进入新区域 | 报最近铃铛方向/距离，不打断探索 |
| 靠近未激活铃铛 | 提醒先敲铃（Boss 前优先级提高） |
| 激活成功 | 确认检查点更新，记入长期记忆 |
| 玩家死亡 | 说明会回到哪个铃铛；若最近铃铛很远，提醒规划路线 |
| 玩家问"最近的铃在哪" | 给方向 + 距离 + 是否已激活；有可靠路线才给路线 |
| 地图层不同 | 明确说"在另一层"，不硬指直线方向 |

不做全自动寻路；只在已有地图数据可靠时给分段方向，门/机关/跳跃让玩家现场确认。

#### 战斗闲聊节奏

```text
接敌前（发现怪群）
  → 一句阵容判断："右前两只近战，后面有个弓手。"

交战中
  → 只在 P0/P1：低血、杀气空、Boss 阶段、危险远程
  → 前摇/大招期间闭嘴，不抢注意力

波次间隙（脱战 2~5 秒）
  → 可以短吐槽/报资源："杀气回一点了，别急着冲。"

胜利
  → 夸具体操作；没有具体操作就短夸，不复读"太棒了"。

死亡
  → 先接情绪，再给一条原因/建议；不训人、不马后炮。
```

**战斗闲聊禁止项**：不在玩家翻滚/格挡判定窗口刷长句；不在过场/处决动画说话；不连续播报同一个敌人；不把"没检测到"说成"安全"。

### 7.7 Boss 前配装建议（只看已装备）

触发：进入 Boss 区域、靠近 Boss 前铃铛、玩家问"怎么打/要不要换"。

输入：

- 已装备主武器（类型、强化等级、铸魂形态）
- 已装备影之武装（类型、充能、冷却）
- 已装备饰品（效果）
- Boss 知识（阶段、攻击类型、场地）
- 玩家历史（是否打过、死过几次；来自本插件记忆）

输出结构：**一句情绪 + 1~3 条随机搭配建议 + 一条退路/铃铛提醒**。建议来自该 Boss 的“已验证建议池”，按当前装备、阶段、剧透等级过滤后随机抽取。

示例（人格无关的结构）：

```text
"这次带的是长形黑伤和追命锁镰啊……它二阶段会拉开距离，锁镰的位移能救急。
先敲铃，喵在门口等你。"
```

规则：

- **每次随机 1~3 条**，不固定同一套；已验证建议不足 3 条就给实际数量，绝不用编造补齐。
- 建议先按“与当前装备相关”加权，再按 relevance × confidence 随机；同一次尝试内不重复。
- 不读背包，不说"你有/你没有"；用条件句："如果手里有远程武装，可以……"
- 不剧透未到阶段，除非 `spoiler_level=2`。
- 不自动换装、不自动使用物品。
- 玩家坚持自己的打法时不纠正；只在明显危险时提醒一次。
- 读不到武器/饰品就只讲 Boss 机制，不猜配装。
- 三条建议优先覆盖不同维度（生存/输出窗口/场地或召唤物），不要三条都在说同一件事。

### 7.8 跨会话记忆（必须）

目标：下次进游戏，猫娘知道"上次卡在哪、怎么打的、约定了什么"，而不是重新认识玩家。

#### 记什么

| 类别 | 示例 | 保留 |
|---|---|---|
| 进度 | 到过哪些区域、当前任务、已激活铃铛 | 长期 |
| Boss 经历 | 尝试次数、死亡次数、最好打到几阶段/多少血、首次击杀 | 长期 |
| 配装 | 上次/当前主武器、影之武装、饰品（只记装备） | 长期 |
| 关系 | 称呼偏好、喜欢/讨厌的玩法、安慰方式、安静请求 | 长期 |
| 约定 | "下次先试幻术琵琶""明天再打沐小葵" | 直到完成/过期 |
| 高光 | 首次击杀、复仇成功、极限翻盘 | 长期 |
| 会话摘要 | 每次结束 3~5 条事实 | 长期 |

#### 不记什么

- 背包内容、材料数量（设计排除）
- 原始截图、键盘输入、完整聊天记录
- 与游戏无关的敏感个人信息

#### 存储

```text
data/memory/pbz_memory.db
  profile(player_key, call_name, preferences_json, quiet_until, updated_at)
  saves(save_key, character_name, started_at, last_seen, game_version)
  encounters(id, save_key, boss_id, boss_name, attempts, deaths,
             best_hp_percent, first_kill_at, last_result)
  sessions(id, save_key, started_at, ended_at, summary, mood_end)
  facts(id, save_key, kind, key, value, confidence, source, first_seen, last_seen)
  promises(id, save_key, text, due_hint, status)
```

- `save_key`：角色名 + 首次铃铛/区域 + 时间；新游戏/NG+ 分开，不把旧进度当成当前档。
- 原始事件保留 90 天，摘要与里程碑长期保留。
- 玩家可在面板查看、删除、导出记忆。

#### 写入与读取

- 高置信事件实时写：Boss 死亡/击杀、铃铛激活、任务完成、区域首次到达。
- 会话结束用 LLM 做摘要，只允许从事件事实里归纳，不允许编。
- 开局把 `memory_digest` 以 `ai_behavior="read"` 注入宿主上下文，用户不可见。
- 聊天中通过 `memory_recall(query)` 工具按需检索。
- 冲突优先级：玩家纠正 > 运行时事实 > 会话摘要。

#### 开局记忆摘要示例

```text
[记忆摘要]
- 上次 11-06：沐小葵 3 次未过，最好打到二阶段 40%
- 常用：长形黑伤 + 追命锁镰；习惯先敲铃再打
- 约定：下次试试幻术琵琶
- 边界：不要剧透第三章之后
```

> 记忆是给宿主人设做“连贯的陪伴”，不是拿来做数据报表。提示词只喂摘要，不喂整库。

### 7.9 职责边界：情绪归宿主，事实归插件

| 层 | 负责 |
|---|---|
| 游戏 Mod | 只读事实、事件、UI 字幕 |
| 插件 | 场景分类、知识检索、记忆摘要、1~3 条建议、语气提示 |
| 宿主 | 当前猫娘人设、称呼、情绪表达、主动/安抚、TTS |
| 玩家 | 纠正、偏好、最终选择 |

规则：

- 插件不写死"喵""主人"等口癖，也不写死安慰句；只给 `facts`、`mood_hint`、`intent`、`memory_digest`。
- 同一件事，傲娇/冰山/病娇人设应该说出完全不同的台词——这是宿主的职责。
- 插件不强迫亲密、不制造依赖、不用内疚感留人。
- 人设可变：换猫娘后，历史记忆仍在，但表达方式跟着新角色变。

### 7.10 更多陪伴玩法（补充）

| 玩法 | 说明 |
|---|---|
| 回归问候 | 隔天再进游戏，先提一件上次的事："上次那只沐小葵，还欠你一次。" |
| Boss 前仪式 | 敲铃 → 看当前装备 → 1~3 条建议 → 一句鼓励，形成固定仪式感 |
| 死亡三段式 | 先接情绪 → 一条可验证原因 → 问"再来一次还是先歇会儿" |
| 胜利复盘 | 夸具体操作，记录首次击杀/最好成绩，提上次失败做对比 |
| 探索闲聊 | 看到地标/风景/新区域，聊感受、问玩家看法，不强塞攻略 |
| 配装身份 | 根据当前武器/武装给"打法标签"（强攻/游走/远程/破障），台词围绕这套打法 |
| 疲劳检测 | 连续多次快速重试、长时间未休息 → 关心一句，建议歇会儿 |
| 共同约定 | 记住"下次先试 X""明天再打"，下次主动提，但不催 |
| 静默陪伴 | 玩家说安静/连续不回应 → 降频甚至不说话，只保留死亡/残血 |
| 新发现 | 新区域、新 NPC、新铃铛、新铸魂形态 → 记录并简短回应，不剧透 |
| 纪念 | 首次击杀、第 10 次尝试、复仇成功等节点写进长期记忆 |

**底线**：以上都必须有事实依据；没有事实就只回应玩家原话，不凭空编游戏事件。

## 8. 画面识别方案

### 8.1 何时截图

- 未知敌人首次出现；
- Boss 出场/阶段变化但结构化字段缺失；
- 玩家问"这是什么/怎么打"；
- 玩家连续死亡 2 次，需要分析死因；
- 每 10 秒最多 1 张；战斗高潮期最多 1 张/5 秒；日预算可配。

### 8.2 截图方式

- 用 Win32 枚举窗口，匹配 `Phantom Blade Zero` / `PBZ`，截取窗口矩形；
- 只截游戏窗口，不截桌面；
- 长边压到 1024，JPEG 80；
- 窗口最小化/被遮挡 → 不截，降级到结构化状态；
- 截图不落盘长期保存，识别后即删。

### 8.3 视觉输出（严格 JSON）

```json
{
  "scene": "combat|exploration|boss|menu|cutscene|death",
  "enemy_count": 3,
  "enemies": [
    {"name": "", "archetype": "ranged", "distance_band": "near", "threat": "high", "confidence": 0.72}
  ],
  "boss": {"name": "", "hp_percent": 62, "phase": 2, "telegraph": "raised weapon"},
```

## 12. 稳定性、性能与兼容

### 12.1 游戏侧

- **绝不抛到主循环**：每个字段读取独立 `try/catch`；采样函数整体再包一层。
- **不每帧扫全场景**：基础状态 4Hz；敌人扫描 2Hz 且受距离限制。
- **UObject 引用不长期持有**：每次采样重新取，避免失效指针崩溃。
- **类名集中**：`game_api.js` 顶部维护 `CLASSES` / `ATTRS` / `TAGS` 常量；补丁改了就改这里。
- **能力探测**：启动时检查关键类/方法是否存在，缺失就降级并在面板显示"不支持项"。
- **热重载**：`main.js` 导出 `stop()`，能干净移除 UMG 控件与定时器。

### 12.2 插件侧

- 桥接读取用异步轮询，不阻塞宿主命令循环。
- LLM 调用有超时（建议 8s）与并发上限；超时直接走模板短句。
- 事件处理串行化，保证同一事件只播一次。
- 所有网络/LLM 失败都不影响游戏。

### 12.3 性能预算

| 项 | 预算 |
|---|---|
| 游戏侧 CPU | <1.5% 单核（4Hz 采样 + 2Hz 扫描） |
| 插件 CPU | <2%（空闲 <0.5%） |
| 内存 | 游戏侧 <30MB，插件 <150MB |
| 截图 | ≤1 张/5s，长边 1024 |
| LLM | 战斗中 ≤4 次/分钟；探索 ≤1 次/分钟 |

### 12.4 兼容性风险

- 游戏补丁可能重命名类/字段 → 需要每次版本更新跑一次 P0 探针。
- UE4SS 本身可能与游戏更新不同步 → 保留纯视觉降级模式（只靠截图 + 键位）。
- 与 `PBZQuestGuide` / `pbz-map-helper` 共存：不修改它们的文件，不抢 F6–F9 热键。

## 13. 安全与边界

- 默认**只读**：不写存档、不改属性、不给物品、不传送。
- 不注入输入：不自动攻击、不自动闪避、不自动走路。
- 桥接文件只写在 `%LOCALAPPDATA%\N.E.K.O\pbz_bridge`，不碰游戏目录以外的用户文件。
- 视觉截图只在本机处理；是否上传取决于用户配置的视觉模型。
- 单机场景使用；不用于联机/竞技或绕过任何在线机制。
- 所有 Mod 文件可一键删除，卸载后游戏恢复原样。
